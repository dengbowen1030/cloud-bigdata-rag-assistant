## 评估目的

原报告用于说明当前系统不是普通聊天问答，而是基于知识库检索结果生成回答的 RAG 系统。评估重点包括：

- 系统是否按“文档上传 -> 解析 -> 切片 -> 向量化 -> FAISS 保存 -> Top-K 检索 -> LLM 基于来源生成答案”的链路工作。
- 用户问题是否能召回相关文档片段。
- 回答是否能和 `sources` 对应起来。
- 检索失败时能否暴露出问题原因，便于后续优化问题表达、切片和召回策略。

## RAG 系统流程

原报告给出的系统整体流程如下：

```text
上传文档
-> 文档解析
-> 文本切片 Chunk[]
-> Embedding 向量化
-> FAISS 保存向量
-> 用户提问
-> Top-K 检索 RetrievedChunk[]
-> LLM 基于来源生成 ChatAnswer
-> 前端展示答案和 sources
```

该流程与项目当前模块契约一致：B/C 阶段产出可检索的 chunk 和向量索引，D 阶段基于 `RetrievedChunk[]` 组织问答，E 阶段展示答案和来源。

## Top-K 检索说明

原报告没有明确写出 Top-K 的数值，但每个表格案例都列出了 5 个按相关度排序的命中 chunk。因此可整理为：报告展示了 Top-K 检索结果，且每个案例展示 5 个候选片段。

Top-K 结果的意义是：系统先从 FAISS 中召回若干相关 chunk，再把这些 chunk 作为上下文来源交给后续问答链路。

## Answer 与 Sources 的关系

原报告中的回答不是孤立生成的，它和表格中的命中文件、chunk_index、正确来源说明对应：

- 案例一回答课程理论内容，对应命中的 `1.pdf`、`4.pdf`、`g.pdf` 中课程相关片段。
- 案例二回答网络爬虫分类，对应 `4.pdf` 中关于爬虫和网络爬虫的片段。
- 案例三首次问题命中偏离，报告说明因为命中内容包含“项目”等关键词但正确页只包含“注意事项”，导致相关度较低；调整问题后回答正确。

这说明系统回答依赖检索来源，同时也暴露了检索对问题表述和关键词匹配的敏感性。

## 为什么可以证明这是 RAG

该报告可以证明系统具备 RAG 特征，原因如下：

- 报告明确列出了从文档上传到 `ChatAnswer` 的完整检索增强生成流程。
- 报告记录了 `Chunk[]`、Embedding、FAISS、Top-K、`RetrievedChunk[]`、`sources` 等关键环节。
- 每个案例都给出了命中文件和 chunk_index，而不是只给模型回答。
- 第三个案例记录了检索失败原因，说明系统确实依赖检索结果，而不是直接让大模型自由回答。
